▼

3. 방법3. 方法10-1

GET과 POST는 요청의 의도를 나타낸다GET 与 POST 表示请求意图 핵심核心

방법方法쉽게 말하면简单来说예例子
GET이미 있는 정보를 보여 달라把已有信息给我기록 목록 불러오기读取记录列表
POST데이터를 보낼 테니 처리해 달라我发数据，请处理새 기록 추가, 입력값 계산添加记录、计算输入值
생각해 보기想一想

“나의 독서 기록을 보여 줘”는 GET, “오늘 읽은 책을 기록해 줘”는 POST에 가깝습니다.“给我看阅读记录”更接近 GET，“记录今天读的书”更接近 POST。

암기보다 의도를 판단합니다不背，而是判断意图

기능이 정보를 받는 일인지, 데이터를 보내 처리하는 일인지만 판단하면 됩니다.只要判断功能是获取信息，还是发送数据并处理。

4. 데이터 형식4. 数据格式10-1

JSON은 ‘이름: 값’으로 데이터를 담는다JSON 用“名称：值”装载数据 핵심核心

JSON은 요청과 응답에서 데이터를 표현하는 방식입니다. Python의 사전과 비슷한 모양입니다.JSON 是请求与响应中表示数据的方式，外形与 Python 字典相似。

요청 JSON请求 JSON
{ "task": "과학 보고서 쓰기" }
응답 JSON响应 JSON
{
  "ok": true,
  "message": "할 일을 추가했습니다."
}
이름名称값值의미意思
task과학 보고서 쓰기写科学报告보낸 할 일发送的待办
oktrue처리 성공处理成功
message추가했습니다已添加화면의 안내画面提示
문법 연습이 아닙니다不是语法练习

괄호와 쉼표를 외우지 않습니다. AI가 제안한 내용에서 이름과 값의 의미를 읽습니다.不背括号和逗号，只读懂 AI 提议中名称与值的意思。

5. 응답5. 响应10-1

성공도 실패도 다음 행동을 알려줘야 한다成功与失败都要告诉下一步 핵심核心

결과结果응답의 내용响应内容화면의 역할画面作用
성공成功성공 여부와 결과是否成功与结果원한 결과 표시显示期望结果
입력 문제输入问题무엇을 고쳐야 하는지要修改什么수정과 다시 시도 방법修改与重试方法
서비스 문제服务问题처리하지 못했음未能处理사용자 탓으로 돌리지 않고 다시 시도 안내不归咎用户，提示重试
더 나은 안내更好的提示

“오류”보다 “할 일을 한 글자 이상 입력한 뒤 다시 추가해 보세요”가 더 유용합니다.比起“错误”，“请输入至少一个字后重试”更有用。

상태 코드를 외우지 않습니다不背状态码

사용자가 결과를 이해하고 다음 행동을 선택할 수 있는지만 확인합니다.只确认用户能否理解结果并选择下一步。

7. 약속표7. 约定表10-1

내 서비스의 핵심 API를 말로 정리한다用语言整理我的核心 API 실습实践

주소와 방법은 AI 제안 후에 적어도 됩니다. 먼저 사용자 행동, 보낼 데이터와 받을 데이터를 자신의 말로 적습니다.地址与方法可在 AI 提议后填写。先用自己的话写用户行动、发送与接收的数据。

  • 사용자의 핵심 행동用户核心行动
  • 요청 주소와 방법 — AI 제안을 받은 뒤에 적는다请求地址与方法 —— 收到 AI 提议后再写
  • 보낼 데이터要发送的数据
  • 성공하면 받을 데이터成功时接收的数据
  • 실패하면 받을 안내失败时接收的提示
  • 응답 뒤 화면에 보여 줄 것响应后画面显示内容
세부 기술 설계는 평가 범위가 아닙니다技术细节不在评价范围

학생은 자신의 흐름에 필요한 요청과 응답의 의미를 설명하면 됩니다.学生只需要说明自己流程中请求与响应的意义。

9. 확인9. 确认10-1

확인 문제检查题

API를 “약속된 창구”라고 하는 이유는 무엇인가?为什么把 API 叫作“约定好的窗口”？
해설 보기查看解析

보내는 쪽과 받는 쪽이 무엇을 어디로 보내고 무엇을 돌려받을지 미리 정해 두었기 때문입니다. 약속이 없으면 화면은 무엇을 보낼지 모르고, 기능은 무엇을 돌려줄지 모릅니다.因为发送方与接收方事先约好了往哪里发什么、又会收到什么。没有约定，画面不知道该发什么，功能也不知道该回什么。

창구라는 말은 정해진 자리라는 뜻입니다. 아무 데나 말을 걸 수 없고 정해진 주소로만 요청합니다.“窗口”指的是固定的位置。不能随便找地方说话，只能往约定的地址发请求。

GET과 POST를 어떻게 구분할 수 있는가?怎样区分 GET 与 POST？
해설 보기查看解析

요청의 의도로 구분합니다. 이미 있는 정보를 보여 달라면 GET, 데이터를 보낼 테니 처리해 달라면 POST입니다.按请求的意图来分。要看已有的信息用 GET，发数据过去让它处理用 POST。

“내 기록을 보여 줘”는 GET, “오늘 읽은 책을 기록해 줘”는 POST입니다. 이름을 외우는 것이 아니라 둘 중 어느 쪽인지 판단하면 됩니다.“给我看我的记录”是 GET，“把今天读的书记下来”是 POST。不是背名字，而是判断属于哪一种。

요청과 응답에서 JSON은 어떤 역할을 하는가?JSON 在请求与响应中起什么作用？
해설 보기查看解析

오가는 데이터를 이름과 값의 쌍으로 담는 그릇입니다. task라는 이름 옆에 값이 있으면, 받는 쪽은 그것이 할 일의 내용임을 알 수 있습니다.它是把往返数据装成名称与值成对的容器。看到 task 这个名字旁边的值，接收方就知道那是待办的内容。

괄호와 쉼표를 외울 필요는 없습니다. AI가 만든 요청·응답에서 어떤 이름에 어떤 값이 들어 있는지 읽으면 됩니다.不必背括号和逗号。只要能在 AI 写出的请求与响应里读出哪个名字装着哪个值就行。

9. 확인9. 确认10-1

확인 문제检查题(이어서)（续）

실패 응답에 사용자가 다시 시도할 정보가 필요한 이유는 무엇인가?失败的响应里为什么要有让用户重试的信息？
해설 보기查看解析

실패했다는 사실만 알려 주면 사용자가 거기서 멈추기 때문입니다. 무엇이 잘못됐고 어떻게 고치는지 알아야 정상 흐름으로 돌아갈 수 있습니다.只告诉他失败了，用户就停在那里了。要知道哪里错了、怎么改，才回得到正常流程。

“오류”보다 “할 일을 한 글자 이상 입력한 뒤 다시 추가해 보세요”가 좋은 응답입니다. 서비스 쪽 문제라면 사용자 탓으로 돌리지 않고 다시 시도할 수 있다고 알려 줍니다.比起“错误”，“请输入至少一个字后再添加”才是好响应。若是服务本身的问题，就不要归咎用户，告诉他可以再试一次。

10회의 API와 11회의 DB는 어떻게 연결되는가?第 10 次课的 API 与第 11 次课的数据库怎样连起来？
해설 보기查看解析

11회에 새 프로젝트를 만드는 것이 아니라, 오늘 만든 요청·응답에 SQLite 저장과 조회를 덧붙입니다. 화면 ↔ API가 화면 ↔ API ↔ SQLite가 됩니다.第 11 次课不是另做一个项目，而是在今天做好的请求·响应上加进 SQLite 的保存与查询。画面 ↔ API 变成画面 ↔ API ↔ SQLite。

그래서 오늘 다시 열었을 때 무엇이 사라지는지 확인해 두는 것이 11회의 출발점이 됩니다.所以今天确认重新打开后什么不见了，就成了第 11 次课的起点。

10. 정리10. 小结10-1

핵심 정리와 완료 확인核心小结与完成确认

  • 사용자 행동이 요청과 응답으로 이어지는 과정을 설명할 수 있다.能说明用户行动如何连到请求与响应。
  • GET과 POST의 기본 차이를 알고 있다.知道 GET 与 POST 的基本差别。
  • JSON의 ‘이름: 값’을 읽을 수 있다.能读懂 JSON 的“名称：值”。
  • 나의 API 약속표에 핵심 내용을 적었다.已在自己的 API 约定表中写下核心内容。
