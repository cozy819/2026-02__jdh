들어가며开始之前9-1

문을 열었는데 아무 말이 없다推开门，却没人说话

이런 장면这样的场景

처음 가 보는 관공서에 들어갔습니다. 안내 데스크도, 번호표 기계도, 안내문도 보이지 않습니다. 창구가 다섯 개 있는데 어디로 가야 하는지 알 수 없습니다.你走进一个第一次去的办事大厅。既没有咨询台，没有取号机，也没有指示牌。窗口有五个，可你不知道该去哪一个。

직원에게 물으니 “저기 서류 쓰고 오세요”라고 합니다. 어떤 서류인지, 다 쓰면 어디로 가는지는 말해 주지 않습니다.问工作人员，回答是“去那边填张表”。至于填哪张表、填完去哪里，没说。

이 건물에 기능이 없는 것이 아닙니다. 창구도 있고 서류도 있고 직원도 있습니다. 없는 것은 사용자가 처음부터 끝까지 지나갈 길입니다.这栋楼不是没有功能。窗口有、表格有、工作人员也有。缺的是让人从头走到尾的那条路。

핵심 질문核心问题

사용자가 이 서비스를 처음 열었을 때부터 원하는 결과를 얻을 때까지
어떤 일을 차례대로 겪게 될까?用户从第一次打开这个服务，到拿到想要的结果，
会依次经历些什么？

앞 차시에서 가져올 것从上一课时带过来的
  • 8-2에서 제출한 PRD에 대표 사용 흐름이 3~4단계로 적혀 있습니다. 오늘은 그것을 더 자세히 펼칩니다.8-2 提交的 PRD 里，代表性使用流程写成了 3~4 步。今天把它展开得更细。
  • 7-2에서 정한 기억할 기록과 다시 확인하는 순간이 흐름 안에 자리를 잡습니다.7-2 定下的要记住的记录与再次查看的时刻，会在流程里各就各位。
  • 6-1에서 화면은 그림 대신 글로 설명했습니다. 흐름도 마찬가지입니다.6-1 里画面用文字而不用图来说明。流程也一样。

1. 순서1. 顺序9-1

사용자 흐름이 먼저인 이유为什么先做用户流程 핵심核心

사용자 흐름user flow用户流程user flow
현상现象
지하철역에는 개찰구, 계단, 승강장이 다 있습니다. 그런데 처음 온 사람이 헤매지 않는 역과 헤매는 역이 있습니다. 시설의 개수가 아니라 지나가는 순서가 안내되어 있는가의 차이입니다.地铁站里检票口、楼梯、站台都有。可有的站第一次来的人不会迷路，有的站会。差别不在设施数量，而在有没有把要走的顺序指出来。
쉬운 설명通俗说法
사용자가 서비스를 처음 열어 목적을 이룰 때까지 지나가는 길입니다.它是用户从打开服务到达成目的所走的那条路。
정확한 정의准确定义
사용자가 목적을 이루기까지 거치는 단계를, 각 단계에서 보는 것 · 하는 행동 · 서비스의 반응으로 이어 붙인 것.把用户达成目的所经过的各个步骤，按每一步的看到什么 · 做什么 · 服务如何回应串接起来。
경계边界
기능 목록은 서비스가 할 수 있는 일을 모아 놓은 것이고, 화면 목록은 화면의 이름을 모아 놓은 것입니다. 둘 다 순서가 없습니다. 흐름에는 순서가 있습니다.功能清单是把服务能做的事列在一起，画面清单是把画面的名字列在一起。两者都没有顺序。流程是有顺序的。
문장 속 사용例句
“이 사용자 흐름은 입력에서 시작해 저장된 기록을 다시 보는 데서 끝난다.”“这条用户流程从输入开始，到再次查看已保存的记录结束。”

개발 계획을 바로 세우면 파일 · 화면 · DB와 무엇부터 만들지에 관심이 쏠리기 쉽습니다. 그러나 서비스에서 먼저 정해야 하는 것은 개발자의 작업 순서가 아니라 사용자가 서비스를 사용하는 순서입니다.一上来就做开发计划，注意力容易全跑到文件、画面、数据库、先做哪个上。可服务里要先定的，不是开发者的工作顺序，而是用户使用服务的顺序。

1. 순서1. 顺序9-1

사용자 흐름이 먼저인 이유为什么先做用户流程 핵심核心(이어서)（续）

흐름을 먼저 정하면 확인되는 것先定流程能确认的事
  • 사용자가 어디에서 시작하고 어디에서 목적을 달성하는가?用户从哪里开始，在哪里达成目的？
  • 각 단계에서 무엇을 보고 무엇을 하는가?每一步看到什么、做什么？
  • 행동 뒤에 서비스는 어떤 반응을 보여 주는가?行动之后服务给出什么反应？
  • 어떤 정보가 다음 단계로 이어지거나 저장되어야 하는가?哪些信息要传到下一步或被保存？
  • 잘못된 입력이나 결과가 없을 때는 어떻게 안내하는가?输入有误或没有结果时，怎样提示？
  • 계획한 기능이 실제 수업에서 만들 수 있는 범위인가?计划的功能是不是课堂上做得出来的范围？
개발에만 쓰는 방법이 아닙니다这不是只用在开发上的方法

행사, 발표, 신청, 제작처럼 여러 단계가 필요한 일을 계획할 때도 같은 방식을 씁니다. 참가자가 무엇을 보고 무엇을 하고 무엇을 돌려받는지 적어 보면 빠진 곳이 드러납니다.活动、发表、报名、制作这类需要多个步骤的事，也用同样的方法来计划。写下参与者看到什么、做什么、得到什么，缺口就露出来了。

2. 두 순서2. 两种顺序9-1

사용자 흐름과 개발 순서는 다르다用户流程与开发顺序不是一回事 핵심核心

사용자 흐름用户流程
  • 서비스를 연다打开服务
  • 필요한 내용을 확인한다确认需要的信息
  • 입력하거나 선택한다输入或选择
  • 실행한다执行
  • 결과를 확인한다确认结果
  • 결과가 기록된다结果被记录下来
  • 저장된 기록을 다시 본다再次查看已保存的记录
개발 순서开发顺序
  • 첫 화면을 만든다做出第一个画面
  • 핵심 기능을 작동시킨다让核心功能跑起来
  • 핵심 기록의 저장과 조회를 연결한다接上核心记录的保存与查询
  • 테스트하고 수정한다测试并修改

왼쪽은 사용자가 겪는 순서이고 오른쪽은 만드는 사람이 일하는 순서입니다. 둘은 길이도 다르고 항목도 다릅니다.左边是用户经历的顺序，右边是做的人干活的顺序。两者长度不同，项目也不同。

순서를 지킵니다顺序不能颠倒

개발 순서는 사용자 흐름과 구현 가능 범위가 확정된 뒤에 만듭니다. 반대로 하면 “만들기 쉬운 것부터” 만들게 되고, 정작 사용자가 목적을 이루는 길은 마지막까지 비어 있게 됩니다.开发顺序要在用户流程与可实现范围确定之后才做。反过来的话，就会“从好做的开始做”，而用户达成目的的那条路，到最后还是空的。

3-2에서 코드를 읽던 방식과 같습니다和 3-2 读代码的方式一样

3-2에서 코드를 입력 · 처리 · 출력으로 나눠 읽었습니다. 사용자 흐름도 보는 것 · 행동 · 반응으로 나눕니다. 대상이 코드에서 사람으로 바뀌었을 뿐입니다.3-2 把代码分成输入 · 处理 · 输出来读。用户流程也分成看到 · 行动 · 回应。只是对象从代码换成了人。

3. 시작과 끝3. 起点与终点9-1

흐름의 시작과 끝을 정한다先定下流程的起点与终点 핵심核心

흐름을 설계할 때는 먼저 시작과 완료 지점을 한 문장씩 적습니다. 가운데 단계는 그 뒤에 채웁니다.设计流程时，先把起点与完成点各写成一句话。中间的步骤随后再填。

틀模板
- 시작: 사용자가 서비스를 처음 열고 ___을 본다.
- 완료: 사용자가 ___을 하고 ___ 결과와 저장된 기록을 확인한다.
채워 넣은 예 — 할 일 정리 서비스填好的例子 — 待办整理服务
- 시작: 사용자가 할 일 정리 서비스를 열고 입력 안내를 본다.
- 완료: 사용자가 할 일을 추가하고, 다시 열어도 목록에 남은 기록을 확인한다.
완료 지점에 기록이 들어갑니다完成点里要有记录

위 예의 완료 문장에는 “다시 열어도 목록에 남은”이 들어 있습니다. 7-2에서 정한 다시 확인하는 순간이 여기에 자리를 잡습니다. 결과를 한 번 보여 주는 데서 끝나면 완료가 아닙니다.上面例子的完成句里有“再打开也还留在列表里”。7-2 定下的再次查看的时刻就落在这里。只把结果展示一次就结束，不算完成。

완료에 필요 없는 기능은 뺍니다与完成无关的功能要拿掉

완료 지점에 도달하기 위해 꼭 필요하지 않은 기능은 핵심 흐름에서 뺍니다. 정렬, 검색, 색 바꾸기 같은 것은 흐름이 완성된 뒤에 생각합니다.为到达完成点并非必需的功能，要从核心流程里拿掉。排序、检索、换颜色之类，等流程完成之后再想。

4. 한 단계4. 每一步9-1

한 단계에는 다섯 가지를 적는다每一步要写五件事 핵심核心

항목项目확인할 질문要确认的问题
사용자가 보는 것用户看到的이 단계에서 화면에 무엇이 보이는가?这一步画面上看得到什么？

이어지는 정보接续的信息다음 단계에서 사용하거나 저장할 정보가 있는가?有没有下一步要用或要保存的信息？

화면의 색상과 정확한 배치, 파일 이름과 코드는 아직 정하지 않습니다. 6-1에서 화면을 글로 설명했던 것과 같은 이유입니다.画面的颜色与确切排布、文件名与代码都还不定。原因和 6-1 用文字说明画面时一样。

5. 표로 쓰기5. 写成表9-1

대표 흐름을 표로 표현한다把代表流程写成表 핵심核心

예 — 할 일 정리 서비스例 — 待办整理服务

단계步보는 것看到的행동行动서비스의 반응服务的反应이어지거나 저장되는 정보接续或保存的信息
1서비스 설명과 할 일 입력란服务说明与待办输入框입력란을 확인한다确认输入框무엇을 입력할지 안내한다提示该输入什么없음无
2입력란과 추가 버튼输入框与添加按钮할 일을 입력하고 추가한다输入待办并添加입력값을 확인한다校验输入的值입력한 할 일输入的待办
3할 일 목록待办列表추가된 항목을 확인한다确认新增的项目새 항목을 목록에 보여 준다把新项目显示在列表里할 일 기록待办记录

10. 오해10. 误解9-1

흔한 오해와 사실常见的误解与事实

오해误解
“흐름은 화면이 여러 개일 때만 필요하다.”“只有画面有好几个时才需要流程。”
사실事实
화면이 하나여도 흐름은 있습니다. 5절의 예는 네 단계가 모두 같은 화면에서 일어납니다. 흐름을 만드는 것은 화면의 개수가 아니라 행동과 반응의 변화입니다.哪怕只有一个画面，流程也存在。第 5 节的例子里四步都在同一画面。构成流程的不是画面数量，而是行动与反应的变化。
오해误解
“예외 상황을 많이 적을수록 꼼꼼한 설계다.”“例外情况写得越多，设计越细致。”
사실事实
지금은 핵심 행동을 막는 예외 하나면 충분합니다. 예외를 늘리면 정상 흐름을 만들 시간이 줄어듭니다. 나머지는 12회 테스트에서 발견해 고칩니다.现在一条挡住核心行动的例外就够。例外一多，做正常流程的时间就少了。其余的到第 12 次课测试时再发现、再改。
오해误解
“어차피 AI가 만들 테니 흐름은 대충 적어도 된다.”“反正 AI 会做，流程随便写写就行。”
사실事实
AI는 흐름이 비어 있으면 스스로 채웁니다. 그렇게 채워진 흐름은 내 서비스의 목적과 다를 수 있고, 다르다는 것을 알아차릴 기준도 없어집니다. 8-2에서 PRD를 맞춘 이유와 같습니다.AI 会把流程的空处自己填上。那样填出来的流程，可能与我服务的目的不同，而且也失去了察觉“不同”的标准。这和 8-2 要对齐 PRD 是同一个道理。
오해误解
“구현이 어렵다는 판정이 나오면 아이디어를 버려야 한다.”“被判定难以实现，就得放弃点子。”
사실事实
대부분은 단순화하면 구현 가능으로 판정됩니다. 목적은 그대로 두고 방법만 바꾸는 것이 정상적인 결과입니다. 9-0의 대안 표가 그 예입니다.多数会被判成简化后可实现。目的照旧，只换方法，这是正常结果。9-0 的替代方案表就是例子。
11. 확인11. 确认9-1

확인 문제检查题

사용자 흐름과 개발 순서의 차이는 무엇인가?用户流程与开发顺序有什么不同？
해설 보기查看解析

주인공이 다릅니다. 사용자 흐름의 주인공은 사용자이고, 개발 순서의 주인공은 만드는 사람입니다.主角不同。用户流程的主角是用户，开发顺序的主角是做的人。

그래서 순서도 다릅니다. 사용자는 “연다 → 입력한다 → 결과를 본다 → 다시 본다”로 가지만, 만드는 사람은 “첫 화면 → 핵심 기능 → 저장 연결 → 테스트”로 갑니다.所以顺序也不同。用户走的是“打开 → 输入 → 看结果 → 再看”，做的人走的是“第一个画面 → 核心功能 → 接上保存 → 测试”。

그리고 사용자 흐름이 먼저입니다. 개발 순서는 흐름과 구현 범위가 정해진 뒤에 만듭니다.而且用户流程在先。开发顺序要在流程与可实现范围定下之后才做。

화면 이름만 나열한 것이 사용자 흐름이 아닌 이유는 무엇인가?为什么只罗列画面名不算用户流程？
해설 보기查看解析

행동과 반응이 빠져 있기 때문입니다. “메인 화면 → 입력 화면 → 결과 화면”을 읽어도 사용자가 무엇을 입력하는지, 서비스가 무엇을 확인하고 무엇을 돌려주는지 알 수 없습니다.因为缺了行动与反应。读“主画面 → 输入画面 → 结果画面”，也不知道用户输入什么、服务校验什么、又给回什么。

각 단계에 “누가 무엇을 했는가?”를 물어 답이 나오면 흐름이고, 답이 안 나오면 목록입니다.对每一步问“谁做了什么？”，答得上来是流程，答不上来是清单。

11. 확인11. 确认9-1

확인 문제检查题(이어서)（续）

정상 흐름을 먼저 정한 뒤 예외 흐름을 정하는 이유는 무엇인가?为什么先定正常流程，再定例外流程？
해설 보기查看解析

예외는 정상 흐름의 어딘가에서 생기기 때문입니다. 정상 흐름이 없으면 예외가 어느 단계에서 벌어지는 일인지 말할 수 없습니다.因为例外总是发生在正常流程的某一步上。没有正常流程，就说不清例外发生在哪一步。

또 정상 흐름이 서비스의 목적이고 예외는 그 목적으로 돌아가는 길입니다. 목적을 정하지 않고 돌아가는 길부터 만들 수는 없습니다.再说，正常流程是服务的目的，例外是回到那个目的的路。目的都没定，就没法先修回去的路。

외부 AI 기능을 원하는 경우 개발 전에 무엇을 확인해야 하는가?想要外部 AI 功能时，开发前该确认什么？
해설 보기查看解析

먼저 그것이 수업 범위 안인지 확인합니다. 외부 AI 서비스 API는 서비스 키와 비용이 필요해 9-0의 제외 목록에 있습니다.先确认它在不在课程范围内。外部 AI 服务 API 需要服务密钥与费用，在 9-0 的排除清单里。

그다음 목적을 유지하는 작은 대안을 찾습니다. 규칙 기반 결과나 교사가 제공한 예시 자료로 바꿀 수 있는지 봅니다.然后找能保住目的的更小替代。看能不能换成基于规则的结果，或老师提供的示例资料。

바꾸었다면 실제 AI 기능이라고 설명하지 않고 수업용 프로토타입이라고 표시합니다. 감추고 시작하는 것이 가장 나쁩니다.换过之后，不得说成是真的 AI 功能，要标记为 수업용 프로토타입（课堂用原型）。瞒着开工是最糟的。

13. 정리13. 小结9-1

핵심 정리核心小结

이번 차시에서 남길 것本课时要记住的
  • 서비스 개발보다 사용자가 서비스를 이용하는 흐름을 먼저 설계한다.比起做开发，先设计用户使用服务的流程。
  • 흐름은 보는 것 · 행동 · 서비스 반응 · 이어지는 정보 · 예외 상황으로 표현한다.流程用看到的 · 行动 · 服务反应 · 接续的信息 · 例外情况来表达。
  • 대표 정상 흐름 한 개와 핵심 예외 흐름 한 개부터 정한다.先定一条代表性正常流程与一条核心例外流程。
  • 화면 이름만 나열한 것은 흐름이 아니다. 행동과 반응이 있어야 한다.只罗列画面名不是流程。要有行动与反应。
  • 화면이 하나여도 흐름은 있다. 행동과 반응이 바뀌면 다음 단계다.只有一个画面也有流程。行动与反应变了，就是下一步。
  • 모든 서비스의 흐름에는 의미 있는 기록이 저장되고 다시 보이는 과정이 포함된다.每个服务的流程里都包含有意义的记录被保存并再次出现的过程。
  • 수업에서 만들기 어려운 기능은 개발 전에 발견하고 목적을 유지하는 작은 대안을 찾는다.课堂上难做的功能要在开发前发现，并找到能保住目的的更小替代。
  • 사용자 흐름과 범위가 확정된 뒤에 개발 순서를 만든다.用户流程与范围确定之后，才做开发顺序。
