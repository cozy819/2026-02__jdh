1. 테스트란1. 什么是测试12-1

한 번 작동한 것과 끝까지 쓸 수 있는 것은 다르다跑通一次和能用到底不是一回事 핵심核心

11-2에서 기록이 저장되는 것을 한 번 확인했습니다. 그런데 기능 하나가 한 번 작동한 것과 사용자가 흐름을 끝까지 마칠 수 있는 것은 다릅니다. 저장은 잘 되는데 안내가 없어 처음 온 사람이 버튼을 못 찾는다면, 그 사람에게 이 서비스는 작동하지 않는 서비스입니다.11-2 已经确认过一次记录能保存。可是一个功能跑通一次，和用户能把流程走完，不是一回事。如果保存没问题，却因为没有说明，第一次来的人找不到按钮，那对这个人来说，这个服务就是不能用的。

사용자 흐름 테스트user flow test用户流程测试user flow test
현상现象
새로 문을 여는 분식집 사장님이 개업 전날 가족을 손님처럼 앉혀 놓고 주문부터 계산까지 해 보게 합니다. 메뉴판이 안 보이는 자리, 계산대가 어디인지 헷갈리는 곳이 그때 드러납니다.新开小吃店的老板，在开业前一天让家人像客人一样坐下，从点餐一直走到结账。看不到菜单的座位、找不到收银台的地方，这时候就暴露出来了。
쉬운 설명通俗说法
만든 사람이 처음 온 사용자인 척 서비스를 처음부터 끝까지 써 보며, 미리 적어 둔 예상과 실제 화면을 맞춰 보는 것입니다.做的人假装是第一次来的用户，把服务从头用到尾，拿事先写好的预想和实际画面对照。
정확한 정의准确定义
사용자 흐름의 상황마다 시작 상태 · 사용자의 행동 · 예상한 서비스 반응을 실행 전에 적고, 실제로 해 본 결과와 비교해 통과 · 실패 · 확인 필요로 판정하는 활동.针对用户流程里的每种情况，在运行前写下起始状态 · 用户的动作 · 预想的服务回应，再和实际试出来的结果比较，判定为通过 · 失败 · 需确认。
경계边界
코드를 읽고 맞는지 따지는 것, 기능이 한 번 되는지만 보는 것은 사용자 흐름 테스트가 아닙니다. 기준은 언제나 사용자가 화면에서 겪는 일입니다.读代码判断对不对、只看功能能不能跑一次，都不算用户流程测试。标准始终是用户在画面上经历的事。
문장 속 사용句中用法
“대표 정상 흐름은 통과했는데, 다시 방문 시나리오에서 기록이 사라져 실패로 판정했다.”“代表性正常流程通过了，但再次访问的场景里记录不见了，所以判定为失败。”
1. 테스트란1. 什么是测试12-1

예상한 반응은 실행하기 전에 적는다预想的回应要在运行之前写

사용자 흐름 테스트는 아래 다섯 단계로 진행합니다. 가장 중요한 곳은 세 번째, 서비스가 보여야 할 반응을 먼저 적는 것입니다. 실행해 본 뒤에 예상을 적으면 화면에 나온 것을 그대로 옮겨 적게 되고, 그러면 모든 줄이 「통과」가 되어 아무것도 확인하지 못한 기록이 됩니다.用户流程测试按下面五步进行。最关键的是第三步：先写下服务应该显示的回应。如果试完才写预想，就会把画面上出现的东西照抄下来，结果每一行都是“通过”，成了什么都没确认的记录。

테스트의 순서测试的顺序
  1. 시작 상태를 정한다. 어느 화면에서, 기록이 몇 개 있는 상태에서 시작하는가.定好起始状态：从哪个画面、在已有几条记录的状态下开始。
  2. 사용자가 할 행동을 정한다. 무엇을 쓰고 무엇을 누르는가.定好用户要做的动作：写什么、按什么。
  3. 예상한 서비스 반응을 적는다. 화면에 무엇이 보여야 하는가.写下预想的服务回应：画面上应该出现什么。
  4. 처음 쓰는 사용자처럼 실행한다.像第一次使用的用户那样运行。
  5. 예상과 실제를 비교해 판정한다.比较预想和实际，做出判定。
3-1에서 하던 순서와 같습니다和 3-1 的顺序一样

3-1에서 코드를 실행하기 전에 결과를 먼저 예상하고, 실행한 뒤 비교했습니다. 대상이 코드에서 사용자가 겪는 화면으로 바뀌었을 뿐 순서는 같습니다.3-1 时，先预想代码的结果再运行，运行后再比较。现在对象从代码换成了用户经历的画面，顺序是一样的。

실패도 결과입니다失败也是结果

예상과 다르게 나온 줄은 지우거나 고쳐 쓰지 않습니다. 실패한 줄이 13회에 무엇부터 고칠지 알려 주는 근거가 됩니다. 실패가 하나도 없는 기록은 대개 제대로 시험하지 않은 기록입니다.和预想不一样的行，不要删掉或改写。失败的行就是第 13 次课决定先改什么的依据。一行失败都没有的记录，往往是没认真测试的记录。

2. 다섯 시나리오2. 五个场景12-1

흐름을 다섯 가지 상황으로 나누어 시험한다把流程分成五种情况来测试 핵심核心

9회에 정한 흐름을 그대로 한 번 해 보는 것만으로는 부족합니다. 처음 온 사람, 실수한 사람, 같은 일을 여러 번 하는 사람, 다음 날 다시 온 사람은 같은 서비스에서 서로 다른 일을 겪기 때문입니다. 이렇게 나눈 상황 하나하나를 시나리오라고 부릅니다. docs/12_test_record.md의 2항 표에는 다섯 시나리오의 이름이 미리 적혀 있습니다.只把第 9 次课定的流程照着走一遍是不够的。第一次来的人、操作失误的人、同一件事做好几次的人、第二天又来的人，在同一个服务里经历的事各不相同。这样分出来的每种情况叫作场景。docs/12_test_record.md 第 2 项的表里，已经写好了五个场景的名字。

2. 다섯 시나리오2. 五个场景12-1

새로고침과 다시 방문은 다르다刷新和再次访问不一样 (이어서)（续）

마지막 시나리오에는 두 가지 행동이 들어 있습니다. 새로고침은 브라우저가 화면을 다시 받아 오는 것이고, 다시 방문은 서비스를 껐다가 다시 켠 뒤 새 탭에서 여는 것입니다. 11-2에서 본 것처럼, 기록이 SQLite 파일에 저장되어 있어야 서비스를 다시 켠 뒤에도 남습니다.最后一个场景里有两个动作。刷新是浏览器重新取一次画面；再次访问是把服务关掉再打开，然后在新标签页里打开。就像 11-2 看到的，记录要存进 SQLite 文件，服务重新打开后才会还在。

새로고침刷新
  • 브라우저에서 F5를 누른다在浏览器里按 F5
  • 서비스는 켜진 채로 있다服务一直开着
  • 화면만 처음부터 다시 그린다只是画面从头重新显示
다시 방문再次访问
  • npm run dev 터미널에서 Ctrl+C로 멈춘다在 npm run dev 的终端里按 Ctrl+C 停止
  • npm run dev로 다시 켠다用 npm run dev 重新启动
  • 브라우저 새 탭에서 localhost:3000을 연다在浏览器新标签页打开 localhost:3000
입력 범위가 있는 서비스만 4항을 씁니다只有输入有范围的服务才写第 4 项

「1부터 100까지」처럼 숫자 범위나 글자 수 제한이 분명한 서비스는 12_test_record.md의 4. 선택 테스트에서 가장 작은 값 · 가장 큰 값 · 허용하지 않는 값을 더 시험합니다. 그런 제한이 없으면 「해당 없음」이라고 적습니다. 다섯 시나리오가 먼저입니다.像“1 到 100”这样有明确数字范围或字数限制的服务，在 12_test_record.md 的 4. 선택 테스트（选做测试）里再测最小值 · 最大值 · 不允许的值。没有这类限制就写“不适用”。五个场景优先。

9. 화면과 표9. 画面与表12-1

화면의 기록과 SQLite Viewer의 줄을 맞춰 본다把画面上的记录和 SQLite Viewer 里的行对一对 핵심核心

기록과 관련된 시나리오는 화면만 보고 통과를 줄 수 없습니다. 화면에 보이는 목록이 정말 data/app.db에서 불러온 것인지, 잠깐 화면에만 남은 것인지는 화면만으로 구별되지 않기 때문입니다. 11-2에서 한 것처럼 SQLite Viewer로 표를 열어 화면과 한 줄씩 맞춰 봅니다.和记录有关的场景，不能只看画面就给通过。因为画面上的列表到底是从 data/app.db 调出来的，还是只暂时留在画面上，光看画面分不出来。像 11-2 那样，用 SQLite Viewer 打开表，和画面一行一行对照。

맞춰 보는 순서对照的顺序
  1. 탐색기에서 data/app.db를 누른다. SQLite Viewer가 열리고 왼쪽에 표 이름이 보인다.在资源管理器里点 data/app.db。SQLite Viewer 会打开，左边能看到表名。
  2. 내 서비스의 기록이 들어 있는 표를 누른다.点存着自己服务记录的那张表。
  3. 화면의 기록 수와 표의 줄 수가 같은지 센다.数一数画面上的记录数和表里的行数是否一样。
  4. 화면에서 가장 최근 기록의 글자와 표의 마지막 줄 값이 같은지 본다.看画面上最新那条记录的文字，和表里最后一行的值是否一样。
화면画面SQLite ViewerSQLite Viewer판정에 쓰는 법怎样用于判定
보인다看得到같은 값의 줄이 있다有同样值的行통과通过
보인다看得到줄이 없다没有那一行실패 — 저장되지 않았다失败 — 没有保存
안 보인다看不到줄이 있다有那一行실패 — 저장은 됐지만 다시 불러오지 못한다失败 — 保存了，但没能调出来
표에서 값을 고치거나 지우지 않습니다不要在表里修改或删除值

SQLite Viewer는 확인만 하는 창입니다. 새 기록이 안 보이면 SQLite Viewer 탭을 닫고 data/app.db를 다시 엽니다.SQLite Viewer 只是用来查看的窗口。看不到新记录时，关掉 SQLite Viewer 标签页，再重新打开 data/app.db。

10. 첫 시험10. 第一次测试12-1

처음 방문 시나리오를 짝과 시험한다和同桌测试首次访问场景 실습实践

오늘 시험해 볼 것은 처음 방문 하나입니다. 만든 사람은 어디를 눌러야 하는지 이미 알기 때문에, 이 시나리오는 내 서비스를 처음 보는 사람이 해 볼 때 가장 정확합니다. 짝과 자리를 바꿔 서로의 서비스를 열어 주고, 만든 사람은 말없이 지켜보기만 합니다.今天要测的只有首次访问一个。做的人早就知道该按哪里，所以这个场景由第一次看到这个服务的人来试最准确。和同桌换座位，互相打开对方的服务，做的人只在旁边默默看着。

순서 — 한 사람에 2분顺序 — 每人 2 分钟
  1. 2항 처음 방문 줄의 앞 세 칸이 채워져 있는지 확인한다. 비어 있으면 지금 채우고 시작한다.确认第 2 项首次访问那行的前三格已经填好。空着就现在填好再开始。
  2. 브라우저 새 탭에 localhost:3000을 열어 둔 채로 짝과 자리를 바꾼다.在浏览器新标签页打开 localhost:3000，然后和同桌换座位。
  3. 짝은 화면을 읽고 처음 하려는 행동을 소리 내어 말한다. 만든 사람은 설명하거나 가리키지 않는다.同桌读画面，把第一个想做的动作说出来。做的人不讲解，也不用手指。
  4. 짝이 머뭇거린 곳, 처음 누르려던 곳을 처음 방문 줄의 실제 결과 칸에 적고 판정한다.把同桌犹豫的地方、第一个想按的地方写进首次访问那行的实际结果格，并做出判定。
짝이 헤맨 곳이 오늘의 수확입니다同桌卡住的地方就是今天的收获

짝이 버튼을 바로 찾지 못했다면 서비스가 잘못된 것이 아니라 안내가 부족한 곳을 찾은 것입니다. 실패로 적고, 짝이 처음에 무엇을 하려고 했는지 그대로 옮겨 둡니다. 13회에 안내 문구를 고칠 때 이 줄을 근거로 씁니다.如果同桌没能马上找到按钮，不是服务坏了，而是找到了说明不够的地方。记成失败，把同桌一开始想做什么原样写下。第 13 次课改说明文字时，就以这一行为依据。

11. 오해11. 误解12-1

흔한 오해와 사실常见误解与事实

사용자 흐름 테스트를 처음 할 때 자주 하는 생각이 세 가지 있습니다. 오늘 쓴 2항과 3항을 다시 보면서 같은 생각으로 쓴 줄이 없는지 확인합니다. 특히 첫 번째 오해는 다음 차시에 실행할 때 기록 전체를 쓸모없게 만듭니다.第一次做用户流程测试时，常有三种想法。回头看看今天写的第 2 项和第 3 项，确认有没有按这种想法写的行。尤其是第一个误解，下一课时运行时会让整份记录都失去作用。

오해误解
“예상은 실행해 보고 나서 맞춰 적으면 된다.”“预想等运行完再照着写就行。”
사실事实
그러면 모든 줄이 통과가 되고 아무것도 비교하지 못합니다. 예상은 반드시 실행 전에 적고, 실행 뒤에는 고치지 않습니다.那样每一行都会通过，什么都比较不了。预想必须在运行前写，运行后不改。
오해误解
“내가 만든 서비스니까 처음 방문은 볼 것도 없다.”“自己做的服务，首次访问没什么可看的。”
사실事实
만든 사람은 이미 알아서 막히는 곳을 못 봅니다. 처음 방문은 처음 보는 사람이 해 봐야 드러납니다.做的人因为早就知道，看不到卡住的地方。首次访问要让第一次看到的人试，问题才会暴露。
오해误解
“화면에 기록이 보이면 저장된 것이다.”“画面上能看到记录，就说明保存了。”
사실事实
화면에만 잠깐 남은 것일 수 있습니다. SQLite Viewer의 줄과 맞춰 보고, 서비스를 다시 켠 뒤에도 보여야 저장된 것입니다.也可能只是暂时留在画面上。要和 SQLite Viewer 里的行对照，服务重新打开后也能看到，才算保存了。

이번 차시에서 남길 것本课时要记住的
  • 사용자 흐름 테스트는 처음 쓰는 사람처럼 끝까지 써 보며 예상과 실제를 비교하는 일이다.用户流程测试就是像第一次使用的人那样用到底，比较预想和实际。
  • 시나리오는 다섯 가지 — 처음 방문 · 대표 정상 흐름 · 예외 뒤 다시 시도 · 같은 행동 반복 · 새로고침·다시 방문.场景有五种 — 首次访问 · 代表性正常流程 · 例外后重试 · 重复同一动作 · 刷新·再次访问。
